## Android 真机：观察结果，而不是只看命令返回

系统控制测试使用无权限、无网络的自有 APK。验证了点击、按键、滑动、全部 95 个
可打印 ASCII 字符，以及主显示 1240×2772 和自有副显示 640×960 的截图。
副显示测试检查主显示夹具没有被误操作。结束后卸载测试 APK，移除自有显示并恢复
原前台。

这里修复的关键问题是目标识别：Android 的逻辑显示 ID 与 SurfaceFlinger 截图 ID
不是同一个编号；不能把一个直接当成另一个使用。现在先建立明确映射，找不到、
名称冲突或映射不唯一就报错。焦点也根据对应显示的窗口 token 关联，无法确认时
报告 unknown/null，不猜测。

其他修复包括：

- 多个设备同时存在时，不自动挑选某个“看起来可用”的设备。
- 切换目标失败后清除旧目标，防止后续操作落回原设备。
- 即使 Android 命令退出码为 0，也检查其明确错误输出。
- 一个操作内的连接和分片读写共用截止时间，慢分片不能无限延长超时。
- 参数错误在整段程序执行前拒绝；截图失败保留调用者已有的文件。

原生 android.type 仍是 Android input text 的可打印 ASCII 通道，排除保留序列 %s；
它没有被宣传为任意应用的通用中文输入。手机网页的 Unicode 输入走另一条经过
实际验证的 CDP 通道。

Android 证据：
https://github.com/LIghtJUNction/zuse/blob/main/docs/evidence/android-physical-2026-11-20.json

该证据保留完整运行与定向复测的区别：17 个检查的最终验证不被写成一次未修改的
全绿运行。

## 手机 Chrome：真实失败推动了一次协议修复

zuse 通过已经授权的 ADB server，把 CDP 消息直接送到手机 Chrome 的调试 socket。
产品不调用 adb 子进程，也不创建本机端口转发。它在现有 Chrome 配置中创建一个
自有标签页，移动端列表只返回这一页，并拒绝选择其他 target。

初次实测在 HTTP discovery 阶段失败。独立对照最终确认：Chrome 已返回 HTTP 200、
Content-Length:447 和完整 JSON，但仍保持连接。旧实现把“连接关闭”当作“响应完成”，
因此错报超时。

修复后按 Content-Length 读取完整响应，不再等待 EOF，并补了保持连接不关闭的
协议回归。短响应、重复或冲突长度、非法长度及不支持的传输编码会明确失败。

最终完整真机运行 **13 项全部通过**：

- 恢复原前台应用后，后台自有标签页继续工作。
- 中文、勾号和 emoji 输入与 DOM 值完全一致。
- Enter 事件被页面观察到。
- 点击事件 isTrusted=true，计数器从 0 变为 1。
- 返回 16 个无障碍节点，夹具密码值不出现在结构化快照中。
- 文本读取包含点击后的实际结果。
- PNG 为 640×480，已核对背景像素 RGB(32,160,96)。
- 外部 target 选择被拒绝后，自有目标仍有效。
- 自有标签页关闭获得确认，原前台保持不变。

测试准备阶段曾短暂打开 Chrome 并等待启动完成，然后在页面操作前恢复原应用。
这说明该手机/版本上的后台控制通过，不代表所有厂商的冻结、锁屏和电源策略都相同。
Chrome 现有配置会被复用，并不是隔离账号配置；测试没有读取现有个人标签页。

## Linux：保留实际验证范围

已验证真实 X11/Xvfb、GTK/AT-SPI、Hyprland 0.57.2 和 Fcitx 路径。发现的输入映射问题
来自临时 Unicode 键盘映射与后台输入之间的关系：前台文字输入现在恢复原映射，
后台输入按真实 XKB plain/Shift 层解析，并在发送任何字符前检查整段文字是否可表示。

私有图形会话通过了前台中文/emoji、后台 ASCII、截图像素与焦点保持等检查。
Caps Lock、Num Lock、非零布局组或按键占用等不支持状态会在键盘效果前拒绝。

共享开发桌面实际通过窗口、坐标和指针检查。键盘步骤发现 Num Lock 开启后停止，
没有把这一项报告成“文字已送达”，也没有擅自切换用户锁定状态。
测试窗口已关闭，原焦点和指针已恢复。

X11 还明确区分“已提交事件”和“应用已经接收”：某些控件可以忽略 XSendEvent。
返回值标明 delivery=submitted、application_confirmation_required=true；
agent 应读取应用状态来确认结果。

证据：
https://github.com/LIghtJUNction/zuse/blob/main/docs/evidence/linux-native-2026-11-20.json

## iOS、macOS、串口和 USB

### iOS

新增原生 Rust HTTP 客户端连接明确的本机 WDA 地址，不依赖 Appium/Node 控制运行时。
支持触摸、滑动、Unicode、原生 UI 树、PNG、启动应用和打开网址。

WDA 必须先完成签名、设备配对并运行；zuse 不自动创建或接管现有会话。替换外部
会话需要显式 replace=true，只删除当前 Runtime 自己拥有且尚未被别人替换的会话。
WDA 没有原子的跨客户端比较并创建接口，多个使用者仍需协调。

默认 JSON source 对原生安全输入字段及其子树脱敏；XML/description 或原始 JSON
需要 raw=true。坐标以 UIKit 点为单位，不能直接把 PNG 像素当作点击坐标。
ios.open_url 跟随系统默认 URL handler，没有提供 Safari DOM/JavaScript 接口。

用户没有可供测试的 iPhone，因此这里明确记为 **20 项 mock/protocol 测试通过**。
文档：https://github.com/LIghtJUNction/zuse/blob/main/docs/ios.md

### macOS

权限发现不主动弹授权框，返回 granted、denied、unknown，并注明结果属于当前进程。
实际输入与截图仍需使用者给真正启动 zuse 的终端、IDE 或应用授权。
Apple Silicon 和 Intel 两个目标通过编译检查；没有把编译等同于 Mac 实机验收。

文档：https://github.com/LIghtJUNction/zuse/blob/main/docs/macos.md

### 串口与 USB

串口 PTY 实测覆盖全部 256 字节双向传输、raw/8N1/115200、80ms 空读超时，以及显式
关闭、Drop、失败后的完整配置恢复。一个 32768 字节背压写入在 15360 字节处超时，
报告的已发送数量与对端实际收到的数量一致，后续步骤没有继续执行。

USB 使用系统 libusb，复用 zsys 动态加载。打开必须指定 bus、address、VID/PID 和
interface；不会自动分离内核驱动。部分写入不会自动重发。bulk/interrupt/control
传输、超时部分数据、无效返回数量以及 release/close/exit/unload 顺序均有 C ABI
夹具验证。

真实设备枚举成功返回 32 个串口候选路径和 9 个 USB 描述符。这不是 32 台实体串口
设备，也不是实体 USB 收发验收。未向未知硬件发送控制测试命令。

USB 只是通用传输接口，具体控制命令仍由设备协议决定。传输 timeout 也不能被解释成
枚举、打开或清理 API 都有同样的硬墙钟上限。原生缓冲区和 DSL 字符串有各自的边界；
base64 场景建议在设备协议允许拆分时采用 32KiB 分块。

文档：https://github.com/LIghtJUNction/zuse/blob/main/docs/device-io.md

## 安装与 MCP

```sh
cargo install zuse-computer --version 0.2.0 --locked
zuse --version
zuse doctor
zuse schema

zuse mcp --stdio
zuse mcp --host 127.0.0.1 --port 8377
zuse mcp --socket /run/user/1000/zuse.sock
```

socket 目录应替换成当前用户的运行目录。库和可执行名为 zuse，Cargo 包名为
zuse-computer。Rust 需要 1.100 或更高版本。

MCP 的 zuse.screenshot 支持 source=desktop、browser、android、ios，使用当前
持久 Runtime 已连接的目标直接返回 PNG。持续多步设备操作和人工协助应使用 shell
或 MCP，以保存会话与设备句柄。原有密码、YubiKey、登录、触碰和许可类人工请求继续
可用；本轮没有要求用户提供账号密码或读取个人页面。

## 仍未宣称完成的范围

没有 iPhone、Mac/Windows 桌面、物理串口外设或任意 USB 设备命令的全面实测。
Android 原生 input text 仍有限制；Chrome 页面 Unicode 已通过真机。
Wayland 后台文字必须能在当前键盘布局的支持层表示，不承诺任意布局的中文后台注入。
独立 Wine 应用、其他 Wayland 合成器与 Safari DOM 也是后续验收范围。

测试记录区分产品修复与夹具修正，保留失败和复测来源；没有把多个不同测试运行、
不同二进制或跨编译结果合并成一项虚构的全平台实测结论。
